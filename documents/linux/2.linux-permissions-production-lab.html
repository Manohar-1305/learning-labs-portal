Linux Permissions - Production Hands-on Lab

Linux Administration | Production Troubleshooting | Practical Exercises

Lab Instructions

You are working as a Linux System Administrator. Your responsibility is to troubleshoot permission issues affecting applications, developers, services, Docker containers, and Kubernetes workloads.

For every scenario, you must reproduce the problem, investigate it, identify the root cause, implement the fix, and verify the result.

Important: Run this lab on a disposable Linux VM. Do not execute these exercises on a production server. Do not use chmod 777 as a shortcut.

Working procedure

  • Execute the environment preparation commands.
  • Create the required files and directories.
  • Reproduce the permission failure.
  • Investigate ownership and permissions.
  • Identify the root cause.
  • Implement your own permission fix.
  • Execute the verification commands.

2. Scenario: Website Returns HTTP 403 Forbidden

Production incident: The deployment team has deployed a new website. Users receive HTTP 403 Forbidden. The web server is running but cannot access website files.

Task 2.1 - Create website files

sudo mkdir -p /opt/linux-permissions-lab/website

echo "<h1>Learning Labs</h1>" | sudo tee /opt/linux-permissions-lab/website/index.html

sudo chown -R root:root /opt/linux-permissions-lab/website

sudo chmod 700 /opt/linux-permissions-lab/website
sudo chmod 600 /opt/linux-permissions-lab/website/index.html

Task 2.2 - Reproduce the failure

id www-data

sudo -u www-data cat /opt/linux-permissions-lab/website/index.html

Expected result: Permission denied.

Task 2.3 - Investigate

ls -ld /opt/linux-permissions-lab/website
ls -l /opt/linux-permissions-lab/website
namei -l /opt/linux-permissions-lab/website/index.html
id www-data
Your task:
  • Identify why the web server cannot read index.html.
  • Check directory traversal permissions.
  • Determine the correct owner and group.
  • Configure least-privilege permissions.
  • Verify that the web server can read the file.
  • Verify that the web server cannot modify the file.

Task 2.4 - Verify your fix

sudo -u www-data cat /opt/linux-permissions-lab/website/index.html

sudo -u www-data test -w /opt/linux-permissions-lab/website/index.html
echo "Write test exit code: $?"

ls -l /opt/linux-permissions-lab/website/

9. Scenario: Kubernetes Pod Cannot Write to Persistent Volume

Production incident: A pod runs as a non-root user but cannot write to its mounted persistent volume.

This exercise uses hostPath for a single-node test cluster. It is not a production storage design. The pod must run on the node containing the host directory.

Task 9.1 - Create the host directory

sudo mkdir -p /opt/linux-permissions-lab/k8s-data
sudo chown root:root /opt/linux-permissions-lab/k8s-data
sudo chmod 755 /opt/linux-permissions-lab/k8s-data

Task 9.2 - Create PersistentVolume and PersistentVolumeClaim

cat <<'EOF' > permission-pv.yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: permission-pv
spec:
  capacity:
    storage: 1Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  hostPath:
    path: /opt/linux-permissions-lab/k8s-data
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: permission-pvc
  namespace: default
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
EOF

kubectl apply -f permission-pv.yaml

kubectl get pv,pvc

Task 9.3 - Deploy a non-root pod

cat <<'EOF' > permission-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: permission-test
  namespace: default
spec:
  containers:
    - name: app
      image: ubuntu:24.04
      command: ["sh", "-c", "sleep infinity"]
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        runAsGroup: 10001
      volumeMounts:
        - name: app-data
          mountPath: /data
  volumes:
    - name: app-data
      persistentVolumeClaim:
        claimName: permission-pvc
EOF

kubectl apply -f permission-pod.yaml

kubectl get pod permission-test
kubectl describe pod permission-test

Task 9.4 - Reproduce the failure

kubectl exec permission-test -- sh -c 'echo "Kubernetes data" > /data/test.txt'

Expected result: Permission denied.

Task 9.5 - Investigate

kubectl exec permission-test -- id

kubectl exec permission-test -- ls -ld /data

kubectl get pv permission-pv -o yaml

kubectl get pvc permission-pvc -o yaml
Your task:
  • Identify the UID and GID running inside the pod.
  • Inspect the host directory permissions.
  • Determine why the non-root process cannot write.
  • Fix the permissions without running the container as root.
  • Test fsGroup and inspect its effect on the mounted volume.

Task 9.6 - Verify

kubectl exec permission-test -- sh -c 'echo "Kubernetes data" > /data/test.txt'

kubectl exec permission-test -- cat /data/test.txt

sudo cat /opt/linux-permissions-lab/k8s-data/test.txt

11. Scenario: Systemd Service Fails Because Script Is Not Executable

Production incident: A systemd service fails to start because its startup script does not have execute permission.

Task 11.1 - Create the startup script

sudo mkdir -p /opt/linux-permissions-lab/systemd-app

sudo tee /opt/linux-permissions-lab/systemd-app/start.sh <<'EOF'
#!/bin/bash
echo "Application started"
sleep infinity
EOF

sudo chown -R labapp:labapp /opt/linux-permissions-lab/systemd-app
sudo chmod 640 /opt/linux-permissions-lab/systemd-app/start.sh

Task 11.2 - Create the systemd service

sudo tee /etc/systemd/system/permission-test.service <<'EOF'
[Unit]
Description=Linux Permission Test Application
After=network.target

[Service]
Type=simple
User=labapp
Group=labapp
ExecStart=/opt/linux-permissions-lab/systemd-app/start.sh
Restart=no

[Install]
WantedBy=multi-user.target
EOF

Task 11.3 - Reproduce the failure

sudo systemctl daemon-reload

sudo systemctl start permission-test.service

sudo systemctl status permission-test.service

sudo journalctl -u permission-test.service -n 30 --no-pager
Your task:
  • Identify the reason the service cannot execute the script.
  • Inspect the script permissions.
  • Check permissions on all parent directories.
  • Correct the issue without running the service as root.

Task 11.4 - Verify

sudo systemctl restart permission-test.service

sudo systemctl status permission-test.service

sudo journalctl -u permission-test.service -n 30 --no-pager
