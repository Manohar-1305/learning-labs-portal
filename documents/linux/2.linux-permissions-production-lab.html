Linux Permissions - Production Hands-on Lab

Linux Administration | Production Troubleshooting | Practical Exercises

Lab Instructions

You are working as a Linux System Administrator in a production environment. Your responsibility is to troubleshoot file and directory permission issues affecting applications, developers, services, Docker containers, and Kubernetes workloads.

Each scenario represents a production incident. You must reproduce the problem, investigate it, identify the root cause, implement the correct fix, and verify the result.

Important: Do not use chmod 777 as a shortcut. Every solution must follow the principle of least privilege. Perform these exercises on a disposable Linux VM.

Rules

  • Read the production incident.
  • Create the required users, groups, files, and directories.
  • Reproduce the reported error.
  • Investigate the actual cause.
  • Fix the issue using appropriate Linux commands.
  • Verify access using the affected user account.
  • Record the root cause and commands used.

1. Prepare Your Linux Environment

Before starting the scenarios, prepare a test environment. You will use these accounts throughout the lab.

Task 1.1 - Create the users

Your task:
  1. Create a user named labdeploy.
  2. Create a user named labapp.
  3. Create a user named labdeveloper.
  4. Create a user named labtester.
  5. Create a user named labbackup.
Verify that all five users exist.

Task 1.2 - Create the groups

Create these groups:
  • labteam
  • labapp
  • labbackup
Add the appropriate users to their corresponding groups. Add both labdeveloper and labtester to labteam.

Task 1.3 - Create the lab directory

Create this directory: 
/opt/linux-permissions-lab
Configure its ownership and permissions so that the lab users cannot modify the lab's root directory.

Verification

id labapp
id labdeveloper
id labtester

getent group labteam
getent group labapp
getent group labbackup

ls -ld /opt/linux-permissions-lab

Continue only after all users, groups, and directories have been created successfully.

2. Scenario: Website Returns HTTP 403 Forbidden

Production incident:

The deployment team has deployed a new website. However, users receive HTTP 403 Forbidden when accessing the website. The web server is running, but it cannot access the website files.

Task 2.1 - Prepare website files

  1. Create a directory named website inside the lab directory.
  2. Create an index.html file.
  3. Put some HTML content inside the file.
  4. Set the ownership to root.
  5. Deliberately configure restrictive permissions.

Task 2.2 - Reproduce the production issue

The web server runs as www-data on Ubuntu/Debian. Use the actual web server account if your distribution uses another account.

  1. Attempt to read index.html as the web server user.
  2. Record the error message.
  3. Check the file permissions.
  4. Check the directory permissions.
  5. Inspect every parent directory in the file path.

Task 2.3 - Troubleshoot

Determine the answers to these questions:

  • Does the web server user have permission to read the file?
  • Does it have execute permission on every parent directory?
  • Who owns the website directory?
  • Which group should have access?

Task 2.4 - Fix and verify

Configure the permissions so that:
  • The web server can read website files.
  • The web server can traverse the website directories.
  • The web server cannot modify website files.
  • Other unauthorized users cannot modify the files.
Verify by reading index.html as the web server user.

Expected outcome: The web server can access the website files without unnecessary write permissions.

3. Scenario: Application Cannot Read Configuration File

Production incident:

An application service fails during startup. The application logs show that it cannot read its configuration file.

Task 3.1 - Create the configuration

  1. Create a directory named config.
  2. Create a file named application.conf.
  3. Add a database host and port to the file.
  4. Set the file owner to root.
  5. Give the file restrictive permissions.

Task 3.2 - Reproduce the issue

Attempt to read the configuration file using the labapp account.

Record:

  • The command executed.
  • The error message.
  • The file owner and group.
  • The directory permissions.

Task 3.3 - Fix the permissions

Configure the directory and file so that:
  • Root retains ownership.
  • The application group can read the configuration.
  • The application user can access the directory.
  • Other users cannot read the configuration.

Task 3.4 - Verify

Test the following:
  1. Can labapp read the configuration?
  2. Can labdeveloper read the configuration?
  3. Can root read the configuration?
Record the result of each test.

4. Scenario: Application Cannot Write to Log Directory

Production incident:

The application starts successfully, but it fails when writing application logs. The application team reports that the log directory is not writable.

Task 4.1 - Prepare the log directory

  1. Create a directory named logs.
  2. Create application.log inside it.
  3. Set root as the owner.
  4. Configure permissions that prevent the application from writing.

Task 4.2 - Reproduce the failure

Execute a command as labapp to append a log entry to application.log.

Capture the permission error.

Task 4.3 - Investigate

Find out:
  • Who owns the log directory?
  • Who owns the log file?
  • Does the application have write permission on the file?
  • Does the application have write and execute permissions on the directory?

Task 4.4 - Fix and verify

Configure the ownership and permissions so that the application can create and append log files, but other users cannot modify them. Verify by writing a new log entry as labapp.

5. Scenario: Developers Cannot Access Shared Directory

Production incident:

Two developers are working on the same project directory. Developer 1 creates a file, but Developer 2 cannot modify it.

Task 5.1 - Create the shared directory

Create: 
/opt/linux-permissions-lab/shared
Set its group ownership to labteam. Initially configure permissions that prevent collaboration.

Task 5.2 - Create a file as Developer 1

Logically simulate Developer 1 by creating a file as labdeveloper. File name: 
project.txt
Add a few lines of text.

Task 5.3 - Reproduce the issue

Attempt to append text to project.txt as labtester.

Record the error and inspect:

  • File owner.
  • File group.
  • File permissions.
  • Shared directory permissions.
  • Group membership of both users.

Task 5.4 - Implement the shared directory solution

Configure the directory so that:
  • Both developers can create files.
  • Both developers can modify shared files.
  • New files inherit the shared group.
  • Unrelated users cannot access the directory.

Task 5.5 - Verify collaboration

  1. Create a new file as labdeveloper.
  2. Inspect its group ownership.
  3. Modify the file as labtester.
  4. Create another file as labtester.
  5. Verify that both users can collaborate.

6. Scenario: SSH Private Key Permission Error

Production incident:

An administrator is unable to connect to a remote Linux server using an SSH private key. SSH reports that the private key permissions are too open.

Task 6.1 - Generate a test SSH key

  1. Create an SSH directory under the lab directory.
  2. Generate an Ed25519 SSH key pair.
  3. Set the private key permissions to an intentionally insecure value.
  4. Set the public key permissions.

Task 6.2 - Reproduce the error

Attempt to use the private key with the SSH client.

Record the SSH warning or error.

Task 6.3 - Troubleshoot

Determine:
  • What permissions does SSH expect on a private key?
  • Should other users be able to read the private key?
  • What should the SSH directory permissions be?
  • Who should own the private key?

Task 6.4 - Fix and verify

Correct the ownership and permissions. Verify the result using ls -l and stat.

Task 7.2 - Reproduce the security issue

8. Scenario: Docker Container Cannot Write to Host Volume

Production incident:

A Docker container runs successfully, but the application cannot write data to its mounted host directory.

Task 8.1 - Prepare the host directory

Create: 
/opt/linux-permissions-lab/docker-data
Configure ownership and permissions so that UID 10001 cannot write to it.

Task 8.2 - Start the container

Use this container configuration:

docker run -d \
  --name permission-test \
  --user 10001:10001 \
  -v /opt/linux-permissions-lab/docker-data:/data \
  ubuntu:24.04 \
  sleep infinity

Task 8.3 - Reproduce the failure

Execute a command inside the container to create: 
/data/test.txt
Record the error message.

Task 8.4 - Investigate

Inspect:
  • The UID and GID of the container process.
  • The host directory owner.
  • The host directory group.
  • The host directory permissions.
Identify why the container cannot write to the mounted directory.

Task 8.5 - Fix and verify

Correct the host directory permissions without running the container as root. Create a file inside the container and verify that it exists on the host.

9. Scenario: Kubernetes Pod Cannot Write to Persistent Volume

Production incident:

An application pod runs as a non-root user. The pod starts, but the application cannot write to its mounted persistent volume.

This exercise uses hostPath for a single-node test cluster. It is not a production storage design. On a multi-node cluster, you must ensure that the pod runs on the node containing the host directory.

Task 9.1 - Prepare the Kubernetes node

Create this directory on the Kubernetes node: 
/opt/linux-permissions-lab/k8s-data
Configure it so that UID 10001 cannot write to it.

Task 9.2 - Create the PersistentVolume and PVC

Use the following manifest as the starting point:

apiVersion: v1
kind: PersistentVolume
metadata:
  name: permission-pv
spec:
  capacity:
    storage: 1Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  hostPath:
    path: /opt/linux-permissions-lab/k8s-data
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: permission-pvc
  namespace: default
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
Save the manifest, apply it, and verify that the PV and PVC are correctly bound.

Task 9.3 - Deploy a non-root pod

Use this pod manifest:

apiVersion: v1
kind: Pod
metadata:
  name: permission-test
  namespace: default
spec:
  containers:
    - name: app
      image: ubuntu:24.04
      command: ["sh", "-c", "sleep infinity"]
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        runAsGroup: 10001
      volumeMounts:
        - name: app-data
          mountPath: /data
  volumes:
    - name: app-data
      persistentVolumeClaim:
        claimName: permission-pvc
Apply the pod manifest and verify that the pod reaches Running state.

Task 9.4 - Reproduce the issue

Execute a command inside the pod to create: 
/data/test.txt
Record the result.

Task 9.5 - Troubleshoot and fix

Investigate the host directory permissions and the security context of the pod. Fix the permission issue without running the container as root. Verify that the pod can create, read, and modify files on the volume.

Additional challenge

Configure and test fsGroup in the pod security context. Compare the volume permissions before and after the change. Check whether your storage driver supports the required ownership or permission changes.

10. Scenario: Administrator Applied chmod 777

Production incident:

An administrator applied chmod 777 to an application directory to resolve a permission issue. Now every local user can modify application files.

Task 10.1 - Create the application directory

Create: 
/opt/linux-permissions-lab/application
Create an application configuration file and assign it to root.

Task 10.2 - Introduce the security problem

Apply permissions that give everyone full access. Attempt to modify the configuration file as labdeveloper.

Task 10.3 - Investigate

Determine:
  • Which users can modify the application files?
  • Why is this configuration unsafe?
  • Which account should own the application files?
  • Which group needs access?
  • Should the application service be allowed to modify its own executable files?

Task 10.4 - Fix

Remove unnecessary permissions. Configure different permissions for directories and regular files. Grant only the access required by the application.

Task 10.5 - Verify

Test read and write access using labapp, labdeveloper, and root.

11. Scenario: Systemd Service Fails Because Script Is Not Executable

Production incident:

A systemd service fails to start after a deployment. The service configuration is correct, but its startup script cannot be executed.

Task 11.1 - Create the startup script

Create: 
/opt/linux-permissions-lab/systemd-app/start.sh
Add a Bash shebang and a command that prints Application started. Configure the script so that the labapp user owns it but cannot execute it.

Task 11.2 - Create the systemd service

Create the following unit file:

[Unit]
Description=Linux Permission Test Application
After=network.target

[Service]
Type=simple
User=labapp
Group=labapp
ExecStart=/opt/linux-permissions-lab/systemd-app/start.sh
Restart=no

[Install]
WantedBy=multi-user.target

Task 11.3 - Reproduce the failure

Reload systemd and attempt to start the service. Inspect the service status and journal logs. Record the exact error.

Task 11.4 - Fix and verify

Correct the script permissions. Restart the service and verify that it starts successfully under the labapp account.

12. Scenario: Incorrect umask Breaks Team Collaboration

Production incident:

A developer creates a new file in a shared directory. Other developers can see the file but cannot modify it.

Task 12.1 - Prepare the directory

Create a shared directory owned by labdeveloper and group labteam. Configure the directory so that new files can inherit the directory group.

Task 12.2 - Reproduce the issue

As labdeveloper:
  1. Set a restrictive umask.
  2. Create a file named restricted.txt.
  3. Inspect the file permissions.
As labtester, attempt to append text to the file.

Task 12.3 - Investigate

Determine:
  • What umask was used?
  • What permissions were assigned to the file?
  • What group owns the file?
  • Why can the second developer not modify it?

Task 12.4 - Fix and verify

Configure a suitable umask for shared team files. Create a new file and verify that labtester can modify it. Also correct the permissions of the existing restricted file.
