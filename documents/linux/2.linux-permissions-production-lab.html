Linux Permissions - Production Hands-on Lab

Production troubleshooting | Permission failures | Ownership | Security

Lab Overview

In this lab, you will reproduce permission-related failures similar to those encountered in Linux production environments.

For every scenario, follow this process:

  1. Understand the production incident.
  2. Create the required users, groups, files, and directories.
  3. Introduce the incorrect permissions deliberately.
  4. Run commands as the affected user and reproduce the failure.
  5. Investigate ownership, permissions, and parent directories.
  6. Apply the correct fix.
  7. Verify that the application or user can perform the required operation.
Run this lab only on a disposable Linux VM or test environment. Do not execute these commands on a production server.

1. Prepare the Lab Environment

Create the lab directory, users, and groups.

sudo mkdir -p /opt/linux-permissions-lab

sudo groupadd labteam
sudo groupadd labapp
sudo groupadd labbackup

sudo useradd -m -s /bin/bash labdeploy
sudo useradd -m -s /bin/bash labapp
sudo useradd -m -s /bin/bash labdeveloper
sudo useradd -m -s /bin/bash labtester
sudo useradd -m -s /bin/bash labbackup

sudo usermod -aG labteam labdeveloper
sudo usermod -aG labteam labtester
sudo usermod -aG labapp labapp
sudo usermod -aG labbackup labbackup

sudo chown root:root /opt/linux-permissions-lab
sudo chmod 755 /opt/linux-permissions-lab

id labapp
id labdeveloper
id labtester

Scenario 1: Web Server Cannot Read Website Files

Production incident: A website returns HTTP 403 Forbidden after a deployment. The web server cannot read the application files.

Step 1: Create website files

sudo mkdir -p /opt/linux-permissions-lab/website

echo "<h1>Learning Labs</h1>" | sudo tee /opt/linux-permissions-lab/website/index.html

sudo chown -R root:root /opt/linux-permissions-lab/website
sudo chmod 700 /opt/linux-permissions-lab/website
sudo chmod 600 /opt/linux-permissions-lab/website/index.html

Step 2: Reproduce the failure

sudo -u www-data cat /opt/linux-permissions-lab/website/index.html

Expected result: Permission denied.

If your distribution does not have the www-data account, replace it with the actual web server service account.

Step 3: Investigate

ls -ld /opt/linux-permissions-lab/website
ls -l /opt/linux-permissions-lab/website
namei -l /opt/linux-permissions-lab/website/index.html
id www-data
Your task: Give the web server account read access to the website files and traversal access to the directories without granting unnecessary write permissions.

Step 4: Fix

sudo chown -R root:www-data /opt/linux-permissions-lab/website

sudo find /opt/linux-permissions-lab/website -type d -exec chmod 750 {} \;
sudo find /opt/linux-permissions-lab/website -type f -exec chmod 640 {} \;

Step 5: Verify

sudo -u www-data cat /opt/linux-permissions-lab/website/index.html

Scenario 2: Application Cannot Read Configuration File

Production incident: An application fails during startup because its service account cannot read the database configuration file.

Step 1: Create configuration

sudo mkdir -p /opt/linux-permissions-lab/config

echo "DB_HOST=localhost" | sudo tee /opt/linux-permissions-lab/config/application.conf

sudo chown root:root /opt/linux-permissions-lab/config
sudo chmod 755 /opt/linux-permissions-lab/config

sudo chown root:root /opt/linux-permissions-lab/config/application.conf
sudo chmod 600 /opt/linux-permissions-lab/config/application.conf

Step 2: Reproduce the failure

sudo -u labapp cat /opt/linux-permissions-lab/config/application.conf

Expected result: Permission denied.

Step 3: Investigate

ls -ld /opt/linux-permissions-lab/config
ls -l /opt/linux-permissions-lab/config/application.conf
id labapp
Your task: Allow the application account to read the configuration without allowing other users to access it.

Step 4: Fix

sudo chown root:labapp /opt/linux-permissions-lab/config
sudo chmod 750 /opt/linux-permissions-lab/config

sudo chown root:labapp /opt/linux-permissions-lab/config/application.conf
sudo chmod 640 /opt/linux-permissions-lab/config/application.conf

Step 5: Verify

sudo -u labapp cat /opt/linux-permissions-lab/config/application.conf

sudo -u labdeveloper cat /opt/linux-permissions-lab/config/application.conf

The application user should be able to read the file. The developer should not.

Scenario 3: Application Cannot Write to Log Directory

Production incident: An application starts successfully but fails when it attempts to write logs.

Step 1: Create log directory

sudo mkdir -p /opt/linux-permissions-lab/logs
sudo touch /opt/linux-permissions-lab/logs/application.log

sudo chown root:root /opt/linux-permissions-lab/logs
sudo chmod 755 /opt/linux-permissions-lab/logs

sudo chown root:root /opt/linux-permissions-lab/logs/application.log
sudo chmod 644 /opt/linux-permissions-lab/logs/application.log

Step 2: Reproduce the failure

sudo -u labapp sh -c 'echo "Application started" >> /opt/linux-permissions-lab/logs/application.log'

Expected result: Permission denied.

Step 3: Investigate

ls -ld /opt/linux-permissions-lab/logs
ls -l /opt/linux-permissions-lab/logs/application.log
Your task: Give the application account the required write access without making the directory writable by everyone.

Step 4: Fix

sudo chown -R labapp:labapp /opt/linux-permissions-lab/logs
sudo chmod 750 /opt/linux-permissions-lab/logs
sudo chmod 640 /opt/linux-permissions-lab/logs/application.log

Step 5: Verify

sudo -u labapp sh -c 'echo "Application started" >> /opt/linux-permissions-lab/logs/application.log'

sudo cat /opt/linux-permissions-lab/logs/application.log

Scenario 4: Shared Directory Access Between Developers

Production incident: Developers can create files, but other team members cannot modify them.

Step 1: Create shared directory

sudo mkdir -p /opt/linux-permissions-lab/shared

sudo chown root:labteam /opt/linux-permissions-lab/shared
sudo chmod 750 /opt/linux-permissions-lab/shared

sudo -u labdeveloper touch /opt/linux-permissions-lab/shared/project.txt

Step 2: Reproduce the failure

sudo -u labtester sh -c 'echo "Updated by tester" >> /opt/linux-permissions-lab/shared/project.txt'

Expected result: Permission denied.

Step 3: Investigate

ls -ld /opt/linux-permissions-lab/shared
ls -l /opt/linux-permissions-lab/shared/project.txt

id labdeveloper
id labtester
Your task: Configure the shared directory so that team members can collaborate and new files inherit the shared group.

Step 4: Fix

sudo chown root:labteam /opt/linux-permissions-lab/shared
sudo chmod 2770 /opt/linux-permissions-lab/shared

sudo chmod g+s /opt/linux-permissions-lab/shared

Start a new login session for users if their supplementary group membership has changed.

Step 5: Verify

sudo -u labdeveloper sh -c 'umask 0002; echo "Created by developer" > /opt/linux-permissions-lab/shared/new-file.txt'

ls -l /opt/linux-permissions-lab/shared

sudo -u labtester sh -c 'echo "Updated by tester" >> /opt/linux-permissions-lab/shared/new-file.txt'

cat /opt/linux-permissions-lab/shared/new-file.txt

Scenario 5: SSH Private Key Permission Error

Production incident: SSH refuses to use a private key because its permissions are too open.

Step 1: Generate a test key

sudo mkdir -p /opt/linux-permissions-lab/ssh

sudo ssh-keygen -t ed25519 \
    -f /opt/linux-permissions-lab/ssh/id_ed25519 \
    -N ""

sudo chown root:root /opt/linux-permissions-lab/ssh/id_ed25519*
sudo chmod 644 /opt/linux-permissions-lab/ssh/id_ed25519
sudo chmod 644 /opt/linux-permissions-lab/ssh/id_ed25519.pub

Step 2: Reproduce the permission issue

ssh -i /opt/linux-permissions-lab/ssh/id_ed25519 localhost

Expected result: SSH warns that the private key is accessible by others and refuses to use it.

Step 3: Fix

sudo chmod 700 /opt/linux-permissions-lab/ssh
sudo chmod 600 /opt/linux-permissions-lab/ssh/id_ed25519
sudo chmod 644 /opt/linux-permissions-lab/ssh/id_ed25519.pub

Step 4: Verify

ls -ld /opt/linux-permissions-lab/ssh
ls -l /opt/linux-permissions-lab/ssh/

For a real SSH login, the key must also be owned by the account using it and stored in an accessible directory.

Scenario 6: Sensitive Configuration Exposed to Unauthorized Users

Production incident: A database configuration file contains credentials and is readable by unauthorized users.

Step 1: Create a sensitive file

sudo mkdir -p /opt/linux-permissions-lab/secrets

echo "DB_PASSWORD=TestPassword123" | sudo tee /opt/linux-permissions-lab/secrets/db.conf

sudo chown root:root /opt/linux-permissions-lab/secrets
sudo chmod 755 /opt/linux-permissions-lab/secrets

sudo chown root:root /opt/linux-permissions-lab/secrets/db.conf
sudo chmod 644 /opt/linux-permissions-lab/secrets/db.conf

Step 2: Reproduce the security issue

sudo -u labdeveloper cat /opt/linux-permissions-lab/secrets/db.conf

Expected result: The unauthorized user can read the credentials.

Step 3: Fix

sudo chown root:labapp /opt/linux-permissions-lab/secrets
sudo chmod 750 /opt/linux-permissions-lab/secrets

sudo chown root:labapp /opt/linux-permissions-lab/secrets/db.conf
sudo chmod 640 /opt/linux-permissions-lab/secrets/db.conf

Step 4: Verify

sudo -u labapp cat /opt/linux-permissions-lab/secrets/db.conf

sudo -u labdeveloper cat /opt/linux-permissions-lab/secrets/db.conf

The application user should be able to read the file. The developer should receive Permission denied.

Scenario 7: Docker Container Cannot Write to a Mounted Directory

Production incident: An application container cannot write to a host-mounted directory because the container process UID does not have write permission.

Step 1: Create host directory

sudo mkdir -p /opt/linux-permissions-lab/docker-data
sudo chown root:root /opt/linux-permissions-lab/docker-data
sudo chmod 755 /opt/linux-permissions-lab/docker-data

Step 2: Run a container as a non-root user

docker run -d \
  --name permission-test \
  --user 10001:10001 \
  -v /opt/linux-permissions-lab/docker-data:/data \
  ubuntu:24.04 \
  sleep infinity

Step 3: Reproduce the failure

docker exec permission-test sh -c 'echo "container data" > /data/test.txt'

Expected result: Permission denied.

Step 4: Investigate

ls -ld /opt/linux-permissions-lab/docker-data

docker exec permission-test id
Your task: Make the host directory writable by the container process without running the container as root.

Step 5: Fix

sudo chown 10001:10001 /opt/linux-permissions-lab/docker-data
sudo chmod 750 /opt/linux-permissions-lab/docker-data

Step 6: Verify

docker exec permission-test sh -c 'echo "container data" > /data/test.txt'

docker exec permission-test cat /data/test.txt

Scenario 8: Kubernetes Pod Cannot Write to Persistent Volume

Production incident: An application pod runs as a non-root user but cannot write to its mounted persistent volume.

This exercise uses hostPath for a single-node test cluster. It is not a production storage design. The pod must run on the node where the host directory exists.

Step 1: Create the host directory on the Kubernetes node

sudo mkdir -p /opt/linux-permissions-lab/k8s-data
sudo chown root:root /opt/linux-permissions-lab/k8s-data
sudo chmod 755 /opt/linux-permissions-lab/k8s-data

Step 2: Create Kubernetes resources

cat <<'EOF' > permission-pv.yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: permission-pv
spec:
  capacity:
    storage: 1Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  hostPath:
    path: /opt/linux-permissions-lab/k8s-data
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: permission-pvc
  namespace: default
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
EOF

kubectl apply -f permission-pv.yaml

Step 3: Create a pod running as UID 10001

cat <<'EOF' > permission-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: permission-test
  namespace: default
spec:
  containers:
    - name: app
      image: ubuntu:24.04
      command: ["sh", "-c", "sleep infinity"]
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        runAsGroup: 10001
      volumeMounts:
        - name: app-data
          mountPath: /data
  volumes:
    - name: app-data
      persistentVolumeClaim:
        claimName: permission-pvc
EOF

kubectl apply -f permission-pod.yaml

kubectl get pod permission-test
kubectl get pv,pvc

Step 4: Reproduce the failure

kubectl exec permission-test -- sh -c 'echo "Kubernetes data" > /data/test.txt'

Expected result: Permission denied.

Step 5: Fix the host directory permissions

sudo chown 10001:10001 /opt/linux-permissions-lab/k8s-data
sudo chmod 750 /opt/linux-permissions-lab/k8s-data

Step 6: Verify

kubectl exec permission-test -- sh -c 'echo "Kubernetes data" > /data/test.txt'

kubectl exec permission-test -- cat /data/test.txt
Additional challenge: Test fsGroup in the pod's securityContext and inspect the resulting volume permissions. Do not assume every storage driver handles ownership changes identically.

Scenario 9: Incorrect chmod 777 Applied to Application Directory

Production incident: An administrator applies chmod 777 to resolve an application access issue, unintentionally allowing every local user to modify application files.

sudo -u labdeveloper sh -c 'echo "unauthorized change" >> /opt/linux-permissions-lab/application/app.conf'

Scenario 10: Systemd Service Fails Because a Script Is Not Executable

Production incident: A systemd service fails to start because its startup script does not have execute permission.

Step 1: Create the script

sudo mkdir -p /opt/linux-permissions-lab/systemd-app

sudo tee /opt/linux-permissions-lab/systemd-app/start.sh <<'EOF'
#!/bin/bash
echo "Application started"
sleep infinity
EOF

sudo chown -R labapp:labapp /opt/linux-permissions-lab/systemd-app
sudo chmod 640 /opt/linux-permissions-lab/systemd-app/start.sh

Step 2: Create the service

sudo tee /etc/systemd/system/permission-test.service <<'EOF'
[Unit]
Description=Linux Permission Test Application
After=network.target

[Service]
Type=simple
User=labapp
Group=labapp
ExecStart=/opt/linux-permissions-lab/systemd-app/start.sh
Restart=no

[Install]
WantedBy=multi-user.target
EOF

Step 3: Reproduce the failure

sudo systemctl daemon-reload
sudo systemctl start permission-test.service

sudo systemctl status permission-test.service
sudo journalctl -u permission-test.service -n 30 --no-pager

Step 4: Fix

sudo chmod 750 /opt/linux-permissions-lab/systemd-app/start.sh

sudo systemctl restart permission-test.service
sudo systemctl status permission-test.service

Scenario 11: Incorrect umask Causes Shared File Access Problems

Production incident: Files created by one team member are not writable by other members of the same group.

Step 1: Create a test directory

sudo mkdir -p /opt/linux-permissions-lab/umask
sudo chown labdeveloper:labteam /opt/linux-permissions-lab/umask
sudo chmod 2770 /opt/linux-permissions-lab/umask

Step 2: Create a file with a restrictive umask

sudo -u labdeveloper sh -c '
umask 0077
touch /opt/linux-permissions-lab/umask/restricted.txt
ls -l /opt/linux-permissions-lab/umask/restricted.txt
'

Step 3: Reproduce the failure

sudo -u labtester sh -c 'echo "Team update" >> /opt/linux-permissions-lab/umask/restricted.txt'

Step 4: Fix

sudo -u labdeveloper sh -c '
umask 0002
touch /opt/linux-permissions-lab/umask/shared.txt
ls -l /opt/linux-permissions-lab/umask/shared.txt
'

For the existing restricted file, correct its permissions separately:

sudo chgrp labteam /opt/linux-permissions-lab/umask/restricted.txt
sudo chmod 660 /opt/linux-permissions-lab/umask/restricted.txt

Step 5: Verify

sudo -u labtester sh -c 'echo "Team update" >> /opt/linux-permissions-lab/umask/restricted.txt'

cat /opt/linux-permissions-lab/umask/restricted.txt

12. Final Production Troubleshooting Challenge

Incident: A deployment has completed, but the application is not functioning correctly.

You have been provided with the following symptoms:

  • The application service cannot read its configuration file.
  • The application cannot write to its log directory.
  • Developers cannot collaborate on files in the shared directory.

Your task

  1. Inspect the ownership of every relevant file and directory.
  2. Check permissions on all parent directories.
  3. Identify the Linux account running the application.
  4. Check supplementary group membership.
  5. Reproduce each failure using sudo -u.
  6. Fix permissions using chmod, chown, chgrp, or ACLs as appropriate.
  7. Verify access as the actual service and developer users.
# Useful investigation commands

whoami
id labapp

ls -l /opt/linux-permissions-lab/
namei -l /opt/linux-permissions-lab/config/application.conf

stat /opt/linux-permissions-lab/config/application.conf
getfacl /opt/linux-permissions-lab/config/application.conf

sudo -u labapp test -r /opt/linux-permissions-lab/config/application.conf
sudo -u labapp test -w /opt/linux-permissions-lab/logs
Completion criteria: The application can read its configuration and write logs. Developers can collaborate through the shared directory. Unauthorized users cannot access sensitive files. No directory or file should require chmod 777.
