Linux File Permissions and Ownership - Real-Time Production Scenarios

In a production server, file permissions decide who can read, change, execute, or access a file or directory.

A permission problem can stop a website, prevent an application from starting, block a deployment, or cause a backup to fail.

In this lesson, we will work through real situations that Linux administrators and DevOps engineers face in production. Each situation includes the problem, investigation commands, the correct fix, and verification.

1. Understanding Linux File Permissions

Every Linux file and directory has an owner, a group, and permissions. These permissions decide what different users can do.

Run the following command to see the permissions of files in the current directory.

Command
ls -l

Example output:

Output
-rw-r--r-- 1 root root 1024 Nov 08 app.conf
drwxr-x--- 2 root developers 4096 Nov 08 reports
-rwxr-xr-x 1 root root  250 Nov 08 deploy.sh

Consider this permission:

Permission structure
- rw- r-- r--
  |   |   |
  |   |   └── Others
  |   └────── Group
  └────────── Owner
Permission Meaning for a file Meaning for a directory
Read (r) View file contents List directory contents
Write (w) Modify file contents Create, delete, or rename entries
Execute (x) Run the file as a program Enter or pass through the directory

2. Numeric Permissions: 755, 644, 750 and 600

Linux also represents permissions using numbers. You will see these numbers frequently in production commands and deployment scripts.

Number Permission
0---
1--x
2-w-
3-wx
4r--
5r-x
6rw-
7rwx

Each number represents the owner, group, or others, in that order.

Permission Typical use
755Directories and executable scripts that others may access
644Publicly readable configuration or website files
750Private application directories
640Files readable by the owner and an approved group
600Private files such as SSH keys
700Private directories such as an SSH directory
Examples
chmod 755 deploy.sh
chmod 644 app.conf
chmod 750 /opt/myapp
chmod 640 /etc/myapp/app.conf
chmod 600 /etc/myapp/secret.env
These are common examples, not rules for every file. Always decide permissions based on which users actually need access.

3. Production Scenario: Website Is Showing Permission Denied

Situation

A company hosts its website on an Ubuntu server using Nginx. The website was working yesterday. After a new deployment, users started receiving a 403 Forbidden error.

The deployment team copied the website files to /var/www/html. However, the Nginx worker cannot read some of the newly copied files.

Website directory:

Directory structure
/var/www/html/
├── index.html
├── css/
│   └── style.css
└── images/
    └── logo.png

Step 1: Check the directory permissions

Command
ls -ld /var/www
ls -ld /var/www/html
ls -l /var/www/html

You may find that the files belong to the deployment user and have permissions that prevent the Nginx worker from reading them.

Step 2: Check which user Nginx is running as

Command
ps -eo user,group,comm | grep nginx

On Ubuntu, the Nginx worker commonly runs as www-data. Confirm the actual user on your server instead of assuming it.

Step 3: Check access to the website files

Command
namei -l /var/www/html/index.html
sudo -u www-data test -r /var/www/html/index.html && echo "Readable" || echo "Not readable"

The first command shows permissions for every directory in the path. The second checks whether the Nginx user can read the file.

Step 4: Apply the correct permissions

If the website files should be publicly readable and deployment ownership is managed separately, use:

Commands
sudo find /var/www/html -type d -exec chmod 755 {} \;
sudo find /var/www/html -type f -exec chmod 644 {} \;

Directories need permission to be entered. Website files need permission to be read. Nginx does not normally need permission to modify website files.

Step 5: Verify the fix

Commands
sudo -u www-data test -r /var/www/html/index.html && echo "Access OK"
sudo nginx -t
sudo systemctl reload nginx

The access test should succeed and the Nginx configuration test should report that the configuration is successful.

Production lesson: Do not give the Nginx user write access to the entire website just to fix a read error. Keep website ownership and deployment access separate.

4. Production Scenario: Application Fails After Deployment

Situation

A company runs a Python application on a Linux server. The application is managed by systemd and runs using a dedicated account called myapp.

The deployment team copies a new release into /opt/myapp. After deployment, the application fails to start.

The service log contains an error similar to:

Example error
PermissionError: [Errno 13] Permission denied:
'/opt/myapp/config/settings.conf'

Step 1: Check the application service

Command
sudo systemctl status myapp
sudo journalctl -u myapp -n 50 --no-pager

Step 2: Check the service user

Command
sudo systemctl show myapp -p User -p Group

Suppose the service runs as myapp. That account must be able to read the application configuration and access the directories it needs.

Step 3: Check the file permissions

Commands
ls -ld /opt/myapp
ls -ld /opt/myapp/config
ls -l /opt/myapp/config/settings.conf
namei -l /opt/myapp/config/settings.conf

The problem may be the file itself or one of the directories leading to it. The application needs permission to pass through each directory in the path.

Step 4: Correct the ownership and permissions

If myapp is supposed to own the application files, correct the ownership of the application directory:

Commands
sudo chown -R myapp:myapp /opt/myapp
sudo find /opt/myapp -type d -exec chmod 750 {} \;
sudo find /opt/myapp -type f -exec chmod 640 {} \;

If the application contains scripts that must be executed directly, restore execute permission only on those scripts.

Example
sudo chmod 750 /opt/myapp/start.sh

Step 5: Test access as the application user

Commands
sudo -u myapp test -r /opt/myapp/config/settings.conf && echo "Config readable"
sudo -u myapp test -x /opt/myapp && echo "Directory accessible"

Step 6: Start the application

Commands
sudo systemctl restart myapp
sudo systemctl status myapp
sudo journalctl -u myapp -n 30 --no-pager
Before running a recursive ownership or permission command, confirm that the entire directory belongs to the application. Do not apply the same permissions to private keys, secrets, executable files, or uploaded data without checking their needs.

5. Production Scenario: Application Cannot Write to Log Files

Situation

A production application is running successfully, but its logs are no longer being written.

The application team reports that the log file has stopped receiving new entries. This makes it difficult to investigate application errors.

Log location:

Directory
/var/log/myapp/
└── application.log

Step 1: Check the log directory

Commands
ls -ld /var/log/myapp
ls -l /var/log/myapp
df -h /var/log

Check the directory owner, file owner, permissions, and available disk space. A full disk can also stop new log entries.

Step 2: Check which user runs the application

Command
sudo systemctl show myapp -p User -p Group

Step 3: Create the log directory with correct ownership

If the application runs as myapp, it should be able to write to its own log directory.

Command
sudo install -d -o myapp -g myapp -m 750 /var/log/myapp

Step 4: Correct the existing log file

Commands
sudo touch /var/log/myapp/application.log
sudo chown myapp:myapp /var/log/myapp/application.log
sudo chmod 640 /var/log/myapp/application.log

Step 5: Test whether the application user can write

Command
sudo -u myapp sh -c 'echo "Permission test" >> /var/log/myapp/application.log'

If the command succeeds, the application user can write to the log file.

Step 6: Check log rotation

Production servers regularly move old logs and create new ones. This is called log rotation. If the new log file is created with the wrong owner or permissions, the application may stop writing to it.

Example logrotate configuration
/var/log/myapp/*.log {
    daily
    rotate 14
    missingok
    notifempty
    compress
    delaycompress
    create 0640 myapp myapp
}

This example keeps 14 rotated daily logs and creates new log files with owner myapp, group myapp, and permission 640.

Production lesson: Fix both the directory and the log file. Also check log rotation, because a correct permission today does not guarantee that the next log file will have the same permission.

6. Production Scenario: Multiple Team Members Need Access to a Directory

Situation

A company has developers, testers, and system administrators. All three teams need access to a shared deployment directory.

One developer creates a file, but another team member cannot edit it. The problem happens because the files are not being created with a shared group.

Shared directory:

Directory
/data/project/

Step 1: Create a shared group

Command
sudo groupadd projectteam

If the group already exists, do not create it again.

Step 2: Add users to the group

Commands
sudo usermod -aG projectteam developer1
sudo usermod -aG projectteam tester1
sudo usermod -aG projectteam admin1

Users may need to start a new login session before the new group membership appears.

Step 3: Assign the shared group to the directory

Commands
sudo mkdir -p /data/project
sudo chown root:projectteam /data/project
sudo chmod 2770 /data/project

The number 2 at the beginning sets the setgid permission. It helps new files and directories inherit the directory's group instead of using the creator's usual group.

Step 4: Check the result

Command
ls -ld /data/project

Expected permission format:

Example output
drwxrws--- root projectteam /data/project

Step 5: Test with a team member

Commands
sudo -u developer1 touch /data/project/test.txt
ls -l /data/project/test.txt
The setgid permission makes new entries inherit the group. It does not automatically guarantee that every new file is group-writable. The user's umask or default access rules must also allow the required write access.

7. Production Scenario: SSH Login Fails Because of Wrong Permissions

Situation

An administrator tries to connect to a production server using an SSH private key. SSH rejects the key even though the key itself is correct.

This can happen when the private key or the SSH directory has permissions that are too open.

Step 1: Check the SSH directory

Commands
ls -ld ~/.ssh
ls -l ~/.ssh

Step 2: Set the correct permissions

Commands
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_rsa
chmod 600 ~/.ssh/authorized_keys

If your private key has a different filename, use that filename instead of id_rsa.

Step 3: Check ownership

Command
ls -ld ~/.ssh
ls -l ~/.ssh

The SSH directory and its files should belong to the account that uses them.

Step 4: Test the connection

Command
ssh -i ~/.ssh/id_rsa user@server-ip
Production lesson: Never make private SSH keys readable by everyone. A private key should only be accessible to the account that needs it.

8. Production Scenario: Application Configuration Contains Database Passwords

Situation

A production application reads its database username and password from a configuration file.

The file is located at /etc/myapp/db.conf. The administrator wants the application to read it, but other users on the server should not be able to read it.

Step 1: Check the application user

Command
sudo systemctl show myapp -p User -p Group

Assume the application runs as myapp. The configuration file can be owned by root and assigned to the application's group.

Step 2: Create the configuration directory

Command
sudo install -d -o root -g myapp -m 750 /etc/myapp

Step 3: Set the file ownership and permission

Commands
sudo chown root:myapp /etc/myapp/db.conf
sudo chmod 640 /etc/myapp/db.conf

With these permissions, root can read and modify the file. Members of the myapp group can read it. Other users cannot read it.

Step 4: Verify access

Commands
sudo -u myapp test -r /etc/myapp/db.conf && echo "Application can read configuration"
sudo -u nobody test -r /etc/myapp/db.conf && echo "Unexpected access" || echo "Other user cannot read configuration"
Never print database passwords or other secrets into terminal output, application logs, or screenshots. Also remember that file permissions protect the file itself; they do not protect a password after an application has exposed it elsewhere.

9. Production Scenario: Docker Application Cannot Access a Mounted Directory

Situation

An application runs in a container and stores uploaded files in a directory mounted from the Linux server.

The application starts successfully, but uploading a file produces a permission error.

Example directory:

Host directory
/data/myapp/uploads/

The application may run as user ID 10001 inside the container, while the directory belongs to a different user on the server. Linux checks the numeric user and group IDs when deciding whether access is allowed.

Step 1: Check the directory ownership

Commands
ls -ldn /data/myapp/uploads
stat -c '%u:%g %a %n' /data/myapp/uploads

Step 2: Check the user ID used by the application

Check the application's configured user ID. For a running container, the following command displays its process users:

Command
ps -eo uid,gid,comm

If you have access to the container's shell, also check:

Command inside the container
id

Step 3: Match ownership with the application's user

If the application is intended to run as UID 10001 and GID 10001, and this directory is dedicated to that application, an appropriate fix is:

Commands
sudo chown 10001:10001 /data/myapp/uploads
sudo chmod 750 /data/myapp/uploads

Step 4: Verify access

Test access using the same user ID and group ID as the application. The application should be able to create and modify files in the mounted directory.

Production lesson: Do not use chmod 777 to solve container permission problems. First check the user ID and group ID used by the application.

10. Production Scenario: Kubernetes Pod Cannot Write to a Persistent Volume

Situation

A company runs an application in Kubernetes. The application stores reports on a Persistent Volume.

The pod starts, but the application fails when it tries to create a report. The application log shows:

Example error
PermissionError: [Errno 13] Permission denied: '/data/reports/report.txt'

The application process may be running as a different user from the owner of the mounted directory.

Step 1: Check the pod

Commands
kubectl get pods -n production
kubectl describe pod myapp-pod -n production
kubectl logs myapp-pod -n production

Step 2: Check the user inside the pod

Command
kubectl exec -it myapp-pod -n production -- id

Step 3: Check the mounted directory

Commands
kubectl exec -it myapp-pod -n production -- ls -ldn /data
kubectl exec -it myapp-pod -n production -- ls -ldn /data/reports

Compare the directory's numeric owner and group with the user and group used by the application.

Step 4: Set the pod's security context

If the storage supports group-based access and the application is designed to run with UID 10001 and GID 10001, the following example can be used as a starting point:

Kubernetes deployment example
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  namespace: production
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      securityContext:
        runAsUser: 10001
        runAsGroup: 10001
        fsGroup: 10001
      containers:
        - name: myapp
          image: myapp:latest
          volumeMounts:
            - name: reports
              mountPath: /data/reports
      volumes:
        - name: reports
          persistentVolumeClaim:
            claimName: reports-pvc

Here, runAsUser sets the user ID for the application process. runAsGroup sets its primary group. fsGroup asks Kubernetes to make supported mounted storage accessible to the specified group.

Step 5: Apply the updated deployment

Command
kubectl apply -f deployment.yaml

Step 6: Verify the pod and directory access

Commands
kubectl rollout status deployment/myapp -n production
kubectl get pods -n production
kubectl exec -it deployment/myapp -n production -- id
kubectl exec -it deployment/myapp -n production -- sh -c 'touch /data/reports/permission-test.txt'
Important: fsGroup does not fix every storage permission problem. Some storage drivers and volume types handle ownership differently. Check the storage provider's behavior before changing a production workload. Do not assume that setting fsGroup will change ownership on every existing volume.

11. Production Scenario: Backup Job Fails Because of File Permissions

Situation

A production server runs a scheduled backup job every night. The backup job suddenly starts failing because it cannot read files from the application directory.

Step 1: Check the backup job logs

Commands
sudo systemctl list-timers
sudo journalctl -u backup.service -n 50 --no-pager

If the backup is managed by cron instead of systemd, check the relevant cron logs for the failed run.

Step 2: Check which user runs the backup

Command
sudo systemctl cat backup.service

Check the service's User and Group settings, or inspect the scheduled job to find the account that runs it.

Step 3: Check the backup directory

Commands
ls -ld /backup
ls -l /backup
df -h /backup

Step 4: Set controlled backup directory access

For example, if a dedicated group called backup is used for backup operations:

Commands
sudo groupadd backup
sudo usermod -aG backup backupuser
sudo chown root:backup /backup
sudo chmod 750 /backup

Add the backup service account to the group only if it is the intended account. A new login session or service restart may be needed for the new group membership to take effect.

Step 5: Verify the backup user's access

Command
sudo -u backupuser test -w /backup && echo "Backup directory is writable"

Also verify that the backup account can read the source directories it is expected to back up.

Production lesson: Backup access should be limited to the required directories. Do not give a backup account unrestricted access to the entire server.

12. Production Incident: Someone Changed Permissions to 777

Situation

An application team cannot upload files. To fix the issue quickly, someone runs:

Unsafe command
chmod -R 777 /var/www/html

The website starts working, but every local user can now modify files in the website directory.

This creates a security risk. A user or compromised process could replace website files or add unwanted code.

Step 1: Find files and directories with open permissions

Commands
find /var/www/html -type d -perm -0002 -print
find /var/www/html -type f -perm -0002 -print

These commands list directories and files that allow everyone to write to them.

Step 2: Review the affected files

Command
find /var/www/html -perm -0002 -printf '%M %u:%g %p\n'

Review the output before making any changes. Some directories may have a specific reason for allowing shared writes.

Step 3: Correct the website permissions

If the website follows the normal arrangement where Nginx only needs to read files, the following can be used after confirming that the directory structure is suitable:

Commands
find /var/www/html -type d -exec chmod 755 {} \;
find /var/www/html -type f -exec chmod 644 {} \;

If some files are executable scripts, restore their execute permissions individually.

Step 4: Verify the permissions

Commands
find /var/www/html -type d -perm -0002 -print
find /var/www/html -type f -perm -0002 -print
ls -l /var/www/html
Never run recursive permission changes across the entire filesystem. A broad command can break SSH, databases, application services, and other production software.

13. Production Scenario: systemd Service Fails with Permission Denied

Situation

An application is installed at /opt/payment-service. The application team has created a systemd service, but the service does not start.

Its log shows:

Example error
Failed to execute /opt/payment-service/start.sh: Permission denied

Step 1: Check the service status

Commands
sudo systemctl status payment-service
sudo journalctl -u payment-service -n 50 --no-pager

Step 2: Check the script permissions

Commands
ls -l /opt/payment-service/start.sh
namei -l /opt/payment-service/start.sh

The script must be executable by the service user. The directories leading to the script must also allow that user to pass through them.

Step 3: Check the script owner and service user

Commands
sudo systemctl cat payment-service
sudo systemctl show payment-service -p User -p Group

Step 4: Correct the script permission

Command
sudo chmod 750 /opt/payment-service/start.sh

Use this permission only if the service user has the required ownership or group access. Also confirm that the script has a valid first line, such as:

Script first line
#!/bin/bash

Step 5: Verify and restart the service

Commands
sudo -u payment test -x /opt/payment-service/start.sh
sudo systemctl restart payment-service
sudo systemctl status payment-service
If the script is executable but still cannot run, check the interpreter path, the filesystem mount options, and the service's security restrictions. Not every execution failure is caused by the file's permission bits.

14. Production Scenario: New Files Are Created with the Wrong Permissions

Situation

A deployment script creates configuration files with permissions that are too open. The administrator wants newly created files to be private by default.

Linux uses a setting called umask to remove permissions when new files and directories are created.

Step 1: Check the current umask

Command
umask

Step 2: Set a more restrictive umask

Command
umask 027

With this setting, a normal file created with default permissions of 666 will normally become 640. A directory created with default permissions of 777 will normally become 750.

Item Default permissions With umask 027
File 666 640
Directory 777 750

Step 3: Test the setting

Commands
touch test.conf
mkdir test-directory
ls -l test.conf
ls -ld test-directory

This setting applies to the current shell and processes started from it. To make it permanent, configure the appropriate user or service environment rather than assuming that a temporary shell setting will affect every application.

Production lesson: A restrictive umask helps prevent newly created files from being readable or writable by users who do not need access.

15. Production Scenario: Finding and Fixing Incorrect Ownership

Situation

An administrator notices that files inside an application directory have different owners. Some belong to root, while others belong to the application account.

This happened because files were created by different deployment processes and users.

Step 1: Inspect ownership

Commands
ls -la /opt/myapp
find /opt/myapp -printf '%u:%g %m %p\n'

Step 2: Identify files that do not belong to the application

Command
find /opt/myapp ! -user myapp -print

This lists files and directories that are not owned by myapp. Review the list before changing anything.

Step 3: Correct only the required ownership

If the entire directory is dedicated to the application and all its contents should belong to the application:

Command
sudo chown -R myapp:myapp /opt/myapp

If only selected files need correction, change only those files instead of changing the entire directory.

Example
sudo chown myapp:myapp /opt/myapp/config/settings.conf

Step 4: Verify ownership

Command
find /opt/myapp -printf '%u:%g %m %p\n'
Never run chown -R against system directories such as /, /etc, or /usr. Changing system ownership can stop important services from working.

16. Useful Linux Permission Commands in Production

Command Purpose
ls -l View file permissions and ownership
ls -ld directory View directory permissions
chmod Change file or directory permissions
chown Change file or directory ownership
chgrp Change the group assigned to a file
id View the current user's ID and groups
groups View group membership
stat View detailed file information
namei -l Check permissions along a complete path
umask View or set default permission restrictions
getfacl View additional access rules
setfacl Set additional access rules

17. Checking Additional Access Rules with ACL

Sometimes a directory must be accessible to a particular user without changing its main owner or group. Linux supports additional access rules for this purpose.

For example, a developer needs read access to a directory, but should not become the owner of the directory.

Give a user read and execute access
sudo setfacl -m u:developer1:rx /data/project

Check the access rules:

Command
getfacl /data/project

Remove the additional rule:

Command
sudo setfacl -x u:developer1 /data/project
ACL rules are useful when the normal owner and group permissions are not enough. Always check the ACL output when permissions look correct but access still behaves unexpectedly.

18. A Safe Method to Troubleshoot Permission Problems

When an application reports permission denied, do not immediately run chmod 777 or change ownership recursively. Follow this order.

  1. Identify the exact file or directory mentioned in the error.
  2. Find which user and group run the application.
  3. Check the owner and permissions using ls -l.
  4. Check every directory in the path using namei -l.
  5. Check whether the application needs read, write, or execute access.
  6. Check additional access rules using getfacl.
  7. Check whether the filesystem is mounted read-only.
  8. Change only the permissions or ownership that need correction.
  9. Test access using the same user that runs the application.
  10. Restart the service only if required and verify its logs.

Complete these tasks on a test Linux server. Do not experiment with permission changes on a production system.

Task 1: Website permissions

  • Create a directory named /var/www/demo.
  • Create an index.html file inside it.
  • Set directory permissions to 755.

Task 2: Application directory

  • Create a user named demoapp.

  • Create /etc/demoapp.
  • Create a file named app.conf.
  • Assign it to root and the demoapp group.

  • Verify that the demoapp user can read it.

  • Create a group named devteam.
  • Create two test users.

  • Create a few test files with different permissions.
  • Find files that allow everyone to write.
  • Review the results.
  • Correct only the files that should not be world-writable.

20. Final Production Checklist

  • Application services run using dedicated users where appropriate.
  • Website files are readable by the web server but not unnecessarily writable.
  • Application configuration files have restricted access.
  • Passwords and private keys are not readable by everyone.
  • Log directories are writable by the correct application account.
  • Log rotation creates files with the correct owner and permissions.
  • Shared directories use the correct group permissions.
  • SSH directories and keys have secure permissions.
  • Container and Kubernetes volume access is checked using actual user and group IDs.
  • Backup jobs have only the access they need.
  • No unnecessary files or directories have permission 777.
  • Recursive permission changes are reviewed before execution.
  • Permissions are tested using the actual service account.

21. What You Should Be Able to Do After This Lesson

After completing these exercises, you should be able to investigate and fix common Linux permission problems found in production.

  • Identify why an application cannot read or write a file.
  • Fix website access problems without giving unnecessary write access.
  • Correct ownership for application files and directories.
  • Secure configuration files containing sensitive information.
  • Manage shared directories for multiple users.
  • Investigate SSH key permission problems.
  • Understand file access problems in containers and Kubernetes.
  • Find unsafe permissions and correct them carefully.
  • Verify fixes using the actual application or service account.

Final Reminder

In production, the goal is not to make every file accessible to everyone. The goal is to give each user and application exactly the access it needs.

When you see a permission error, identify the user, check the file, inspect the complete directory path, and test the access. Make the smallest required change and verify the result.
